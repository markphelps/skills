This section names the three regions, shows their proportions in two specimens, and lists what the file does and does not store. The following parts take each region in turn.

The regions

The length, N. Bytes [0, 8). An unsigned 64-bit little-endian integer giving the size of the header in bytes. The eight-byte length covers its limits.

The header. Bytes [8, 8 + N). One UTF-8 JSON object. Each key is a tensor name and each value records a dtype, a shape and a pair of data_offsets. One reserved key, __metadata__, holds a string-to-string map.

The data section. Bytes [8 + N, end of file). The README calls it the "byte-buffer". The tensors' raw bytes, back to back, with no gaps, no overlap, no alignment padding between them, and no trailer.

The left column is the complete content of the header structs at tensor.rs:539–546 and tensor.rs:799–806. The right column is the absence of any corresponding field or check in tensor.rs.

The first row of the right column has a practical cost. A reader cannot recognise a safetensors file from its first bytes. The first eight bytes of tiny.safetensors are 40 00 00 00 00 00 00 00, which is also a valid start for many other things. The file is identified by its header parsing and its offsets adding up, as The checks, in order shows.

This section prints a whole file, decodes it in five steps, and checks the result two ways. The file was written by save_file({"test": np.arange(4, dtype=np.int32).reshape(2, 2)}, …) in research/make_specimens.py.

$ python3 -c "import sys; sys.stdout.write(open('research/specimens/tiny.safetensors','rb').read().hex(' ', 1))"

Step by step

  1. Length. Bytes [0, 8) are 40 00 00 00 00 00 00 00. Little-endian, that is 0x40 = 64. So N = 64 and the header is [8, 72).
  2. Header text. Bytes [8, 72) are ASCII: {"test":{"dtype":"I32","shape":[2,2],"data_offsets":[0,16]}} followed by four 20 bytes. The JSON is 60 bytes; 60 is not a multiple of 8, the next multiple is 64, so the writer added 4 spaces.
  3. Entry. One key, test. Its dtype I32 is 32 bits per element. Its shape [2, 2] has 2 × 2 = 4 elements. 4 × 32 bits = 128 bits = 16 bytes. Its data_offsets are [0, 16), and 16 − 0 = 16. The declared range and the computed size agree.
  4. Absolute position. Offsets are relative to the data section, which starts at 8 + 64 = 72. The tensor is at [72 + 0, 72 + 16) = [72, 88).
  5. Coverage. The last tensor ends at relative offset 16. 8 + 64 + 16 = 88, which is the file size. Nothing is left over.

Checking the decode

The independent parser and the reference library give the same answer:

$ python3 research/parse.py research/specimens/tiny.safetensors
file_size=88 N=64 json_len=60 pad=4 data_start=72 data_len=16
  test    I32   [2, 2]    rel [0, 16)  abs [72, 88)    16 B
from safetensors import safe_open
with safe_open("research/specimens/tiny.safetensors", framework="np") as f:
    print(f.get_tensor_meta("test"), f.get_tensor("test").tolist())
# TensorMeta { dtype: "I32", shape: [2, 2], data_offsets: (0, 16) } [[0, 1], [2, 3]]

The same file appears in the crate's own documentation with a different padding. The doc-test for SafeTensors::deserialize builds its input as b"<\x00\x00\x00\x00\x00\x00\x00{\"test\":{…}}" tensor.rs:437: < is 0x3C = 60, so that header is 60 bytes with no padding, and the reader accepts it. How the writer orders and pads explains why the writer's own output has the four spaces.
